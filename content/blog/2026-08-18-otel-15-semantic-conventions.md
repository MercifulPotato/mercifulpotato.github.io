## Part 1: Same Fact, Five Names

Part 14 of this series established that OTLP guarantees any two OpenTelemetry-speaking systems can exchange bytes and agree on their shape: this is a span, it has this trace ID, it has these attributes. What OTLP does not guarantee, on its own, is that two systems agree on what those attributes are actually called. Imagine five different teams, each independently instrumenting their own HTTP-handling code before any shared convention existed, recording the exact same underlying fact — the numeric status code an HTTP response carried — under five different attribute names: `http.status`, `status_code`, `httpStatusCode`, `code`, `response.status`. Every one of these names is a perfectly reasonable choice made in isolation. Together, they make it functionally impossible to write one query, one dashboard, or one alert rule that works consistently across all five teams' services, because a system built on any one name is blind to the same fact recorded under any of the other four.

This is precisely the phone-book problem: a phone book is only useful if everyone agrees to list "smith, john" the same way, in the same place, rather than one person filing it under "j" and another under "s." Today's post covers the specific, formal mechanism OpenTelemetry uses to solve this exact problem — semantic conventions — and, honestly, one of the more painful, real episodes in the project's own history when getting this dictionary right required breaking things that were already working.

## Part 2: What Semantic Conventions Actually Are

A semantic convention, in OpenTelemetry's own formal vocabulary, is an agreed, published specification of what a given piece of telemetry data should be named and how it should be structured, so that "the HTTP status code of this request" is represented identically no matter which team, which company, or which programming language produced it. This series has been quietly relying on semantic conventions throughout, without always naming them directly: the `service.name` and `service.version` resource attributes from Part 12, the `order.id` and `payment.gateway` attributes on our checkout spans since Part 6, and the `deployment.environment` attribute our Collector configuration in Part 13 inserted are all examples of the kind of agreed, structured naming this dictionary exists to standardize — though it is worth noting explicitly that `order.id` and `payment.gateway` are our own application-specific attributes, not part of the published dictionary itself, precisely because no shared convention could reasonably anticipate every business's own specific domain vocabulary. Semantic conventions cover the common, cross-cutting concepts — HTTP, databases, messaging systems, exceptions — that recur across nearly every application, regardless of what that application's specific business happens to be.

A distinct but closely related category, worth naming precisely here because it recurs throughout this series, is the resource attribute: information identifying not what a specific operation was about, but who — which service, which version, which environment — actually produced this telemetry in the first place. `service.name`, introduced back in Part 12's `ConfigureResource` call, is the resource attribute this series has relied on most heavily.

## Part 3: A Stabilization Case Study, Told Honestly

The HTTP semantic conventions offer this series' clearest, best-documented case study of exactly how difficult this dictionary-building work has turned out to be in practice, and the project's own migration documentation is unusually candid about it.

Consider the single most basic fact an HTTP span could record: which HTTP method was used. In the conventions' earlier, pre-stable form, this lived in an attribute named `http.method`. When the HTTP conventions reached their stable release, verified directly against the project's own current migration documentation, that attribute was renamed to `http.request.method` — and, notably, its behavior changed alongside its name, now capturing only nine common HTTP methods by default, with anything else recorded as a generic `_OTHER` value, configurable if an application genuinely needs finer detail. The status code attribute underwent the identical pattern: `http.status_code` became `http.response.status_code`. And these were far from the only changes; the same migration renamed the URL-related attributes entirely, splitting what had been a single `http.target` attribute into two separate attributes, `url.path` and `url.query`, and renamed the network-level attributes describing client and server addresses in a similarly thorough overhaul.

Why would a mature, widely used specification put its own users through this kind of disruptive renaming rather than simply living with the earlier names forever? The honest answer is that the earlier names, chosen before the wider pattern across many different protocols had become fully clear, turned out not to generalize cleanly once the project tried to apply the same consistent structure across HTTP, databases, messaging systems, and remote-procedure-call frameworks all at once. Names like `request.method` and `response.status_code`, nested consistently under their own namespace, generalize far better across many different kinds of network protocols than a flatter, HTTP-specific `http.method` ever could, and getting this structural consistency right, even at the cost of a disruptive one-time rename, was judged worth the pain of breaking existing dashboards and queries built on the earlier names.

Recognizing that this exact tension — breaking real, already-deployed instrumentation in the name of long-term correctness — is a genuinely serious cost, the project built a specific, formal migration mechanism rather than simply flipping a switch overnight. Instrumentation libraries transitioning to the stable conventions were required to support an environment variable, `OTEL_SEMCONV_STABILITY_OPT_IN`, accepting one of two values during the transition: `http`, which emits only the new, stable names, or `http/dup`, which emits both the old and the new names simultaneously, side by side, letting a team update its dashboards and queries gradually rather than being forced to do so in one disruptive, all-at-once cutover. The project's own migration guidance further required that instrumentation supporting this dual-emission mode be maintained, with at least security patching, for a minimum of six months after the stable names became available — a genuinely concrete, dated commitment to giving real users real time to migrate, rather than an abstract promise of eventual compatibility.

## Part 4: Why It Moves Slowly, on Purpose

The episode above should make plain why semantic conventions, as a category, evolve considerably more slowly and cautiously than most other parts of this series' architecture. Every proposed convention has to work reasonably well across an enormous diversity of backends, each with its own storage model, its own query language, and its own ideas about what makes a good dashboard — a constraint this series has not had to grapple with nearly as directly in earlier posts, since the SDK and Collector layers, covered in Parts 10 through 13, could be designed with considerably more architectural freedom.

There is a second, closely related discipline conventions must maintain: guarding carefully against cardinality explosion, exactly the problem Part 8 of this series introduced in the context of metrics. Notice, in the migration table above, that certain server-address attributes moved from a status of "recommended" to a status the project calls "opt-in," specifically flagged as carrying a "high-cardinality vulnerability" because their values are drawn from raw, attacker-influenceable HTTP headers — a genuinely careful, deliberate design response to precisely the cardinality-bomb risk this series warned about explicitly in Part 8's discussion of metrics attributes, now applied to the naming layer itself.

The project's own honest, self-critical account of the cost of this caution, referenced already in Part 18's preview and worth restating here in its proper context: many instrumentation libraries remain stuck on pre-stable, experimental versions specifically because they depend on semantic conventions that have not yet themselves reached a stable release, leaving outside contributors caught between shipping unspecified, potentially soon-to-be-renamed telemetry, or engaging with a standardization process that, as this very case study demonstrates, can take genuine years to settle a single protocol's naming.

## Part 5: New Territory, Carefully Hedged

Semantic conventions continue expanding into genuinely new domains, and the newest, most actively developing example as of this writing covers generative artificial intelligence systems — attributes describing calls to large language models, the tokens consumed, the specific model used, and related concepts. This is worth flagging with exactly the same care this series has applied to every other fast-moving claim throughout: this is new, active work, and precisely because Part 4's four-stage maturity ladder applies here as directly as anywhere else in this series, a reader encountering claims about generative-AI semantic conventions should verify the current stability status directly against the project's own registry rather than assuming any particular level of maturity from this post alone, since by the time you are reading this, the specifics may well have moved again.

## Part 6: How to Spot the Lie — The Cross-Service Comparison Chart

A dashboard comparing latency, error rate, or any other metric across several different services, presented as though it were a simple, neutral, apples-to-apples comparison, deserves a specific, pointed question in light of everything this post has just covered: if those services were built by different teams, at different times, quite possibly before a given convention had stabilized, is it actually certain that each service is naming and structuring the underlying field identically?

Very often, the honest answer is no — someone, somewhere, had to write a translation layer, quietly mapping one service's older, pre-stable `http.method` attribute onto another, newer service's `http.request.method` attribute, so that the comparison chart could pretend the underlying data always looked the same. That translation is not inherently dishonest, and it is often necessary, sensible work. But it is a choice, made by a person, about how to reconcile genuinely different underlying data — and a choice like that can silently introduce its own small distortions, particularly around exactly the edge cases this post's case study surfaced: what happens to a request using an HTTP method outside the nine common ones the stable convention captures by default, or to a URL whose path and query were once combined and are now split. The test this section offers, then, is simply to ask, directly: what mapping was applied to make this comparison possible, and what, if anything, quietly failed to survive that mapping intact?
